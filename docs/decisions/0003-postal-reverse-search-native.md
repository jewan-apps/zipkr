# ADR-0003: 우편번호 5자리 역검색 — 행안부 API native 활용

| 항목 | 내용 |
|---|---|
| 상태 | 승인됨 |
| 날짜 | 2026-05-05 |
| 결정자 | jewan |
| 적용 범위 | zipkr v1.1f |
| 관련 PR | #17 |
| 준수 헌법 | `JEWAN_DEV_CONSTITUTION.md` §2.2 (기술 교체 가능성), §8 (기술 도입 심사) |

---

## 컨텍스트
zipkr v1.0 출시 직후 사용자 피드백에서 "우편번호로 주소를 찾고 싶다"는 요구가 반복적으로 들어왔다. 기존 검색 흐름은 도로명·지번·건물명 keyword만 다뤘고, 5자리 숫자가 입력되면 `SearchUiState.Phase.PostalCodeUnsupported` 분기로 빠져 "지원하지 않아요" 안내 화면을 노출하던 상태였다.

검증 단계에서 행안부 도로명주소 검색 API(`addrLinkApi.do`)의 `keyword` 파라미터가 5자리 숫자 입력을 우편번호로 native하게 해석한다는 사실이 확인됐다. 추가 외부 API 없이 기존 호출 경로만으로 역검색 기능을 통합할 수 있는 상태였다.

## 결정
**행안부 keyword 파라미터에 5자리 숫자를 그대로 전달**해 우편번호 역검색을 구현한다. 별도 `PostalCodeProvider` 추가나 신규 외부 API 도입 없이 기존 `JusoAddressProvider` 호출 경로를 재사용한다.

흐름:
1. 사용자가 5자리 숫자를 입력한다 ("06236")
2. `SearchViewModel.effectiveQuery`에서 sido 합성을 건너뛴다 — sido가 선택돼있어도 5자리 숫자면 raw query 그대로 전달 ("서울특별시 06236" 합성은 행안부에서 빈 결과)
3. 행안부 API에 keyword="06236"로 호출 → 해당 우편번호의 도로명주소 목록 반환
4. 빈 결과인 경우 `EmptyResultPanel`에서 "해당 우편번호의 주소가 없어요" 분기 노출

기존 `Phase.PostalCodeUnsupported`는 데드 코드로 완전 제거한다 (헌법 §1.4 SRP + `feedback_dead_code_removal`).

---

## 6단계 심사

### 1. 필요성
사용자 피드백에서 우편번호 역검색이 v1.0 출시 후 가장 반복적으로 요청된 기능이다. 우편번호만 들고 있는 사용자(택배 송장·청구서·등기우편 수신자 등)가 "이 우편번호가 어디 주소냐"를 묻는 use case가 명확하다. 행안부 native 지원이 있으면 외부 API 추가 부담 없이 즉시 처리 가능.

### 2. 대안 (최소 2개)
- **A. 별도 `PostalCodeProvider` 추가**: 우편번호 검색만 담당하는 신규 Provider 클래스 도입. SRP 관점에선 깔끔하지만 행안부 API가 이미 우편번호를 처리하므로 wrapper 한 겹 더 두는 게 과한 추상화. 헌법 §3.2(과한 추상화 금지) 위반.
- **B. 행안부 keyword native 활용** (선택): 5자리 숫자를 raw query 그대로 행안부에 전달, ViewModel에서 sido 합성만 건너뛰는 가드 추가. 신규 의존성 0, 신규 클래스 0, 변경 최소.
- **C. 우체국 OpenAPI 신규 통합**: 우편번호 전용 공식 API. 데이터 신뢰도 최상위지만 신규 API 키 발급 + 인증 + 의존성 추가 부담. 행안부가 이미 native 지원하는 상황에선 over-engineering.
- **D. 자체 우편번호 DB 번들링**: 5자리→주소 로컬 sqlite 번들. APK 크기 +수 MB, 데이터 갱신 주기 문제, "이미 행안부가 한다"는 사실 앞에서 정당성 부재.

### 3. 트레이드오프
- ✅ 신규 의존성 0개, 신규 외부 API 0개 — 헌법 §8 (승인 없는 신규 의존성 금지) 자동 준수
- ✅ 코드 변경 최소: ViewModel에 5자리 가드 1줄, Phase 1개 제거, EmptyResultPanel 분기 1개 신설
- ✅ 응답 시간 변화 없음 — 기존 행안부 호출 1회 그대로
- ⚠️ sido prefix 합성을 건너뛰는 분기 로직이 ViewModel에 추가됨 — 가드 1줄 수준이라 SRP 영향 미미
- ⚠️ 행안부 API가 미래에 5자리 native 지원을 철회할 가능성(낮음) — 그 경우 `PostalCodeProvider` 추가로 전환 비용 작음

### 4. 동작 원리
- 행안부 도로명주소 검색 API는 `keyword` 파라미터의 입력값을 자체 인덱스에서 매칭한다.
- 인덱스에는 도로명·지번·건물명과 함께 **우편번호 컬럼이 포함**돼있어, 5자리 숫자 입력은 우편번호 컬럼 매칭으로 처리된다.
- 응답 스키마는 일반 keyword 검색과 동일 — `roadAddr`, `jibunAddr`, `zipNo`, `engAddr` 등 모든 필드 그대로.
- 따라서 UI/도메인 계층은 입력 분기만 처리하면 되고, 데이터 계층은 변경 0.

### 5. 원래 목적
행안부 도로명주소 검색 API는 "사용자가 알고 있는 주소 단편으로 정규화된 주소를 찾는다"가 본래 목적. 도로명·지번·건물명·우편번호는 모두 정규화된 주소를 가리키는 식별자 단편이며, 우편번호 검색은 API 설계 의도의 정상 use case다.

### 6. 유사 기술 비교
| 측면 | 행안부 keyword native | 별도 우체국 API | 자체 DB 번들 |
|---|---|---|---|
| 신규 의존성 | ❌ | ✅ API 키·인증 추가 | ✅ APK +수 MB |
| 데이터 갱신 | 자동 (서버) | 자동 (서버) | 수동 (앱 업데이트 필요) |
| 응답 정확도 | ✅ 행안부 공식 | ✅ 우체국 공식 | ⚠️ 갱신 시점 의존 |
| 구현 비용 | ★ (가드 1줄) | ★★★ (신규 통합) | ★★★★ (DB 번들 + 갱신) |
| 헌법 §8 부합 | ✅ | ❌ (신규 의존성 심사) | ❌ (대규모 변경) |

→ **행안부 native가 zipkr 단계에서 압도적 합리**. 외부 API/DB가 필요한 시점은 행안부가 처리하지 못하는 케이스가 나왔을 때.

---

## 영향
- **신규 의존성**: 없음
- **사용자 가시 변화**: 우편번호 5자리 입력 시 "지원하지 않아요" → 실제 검색 결과 또는 "해당 우편번호의 주소가 없어요" 안내
- **strings.xml**: `postal_code_unsupported_*` 제거, `empty_zip_results_*` 신설
- **데이터 흐름 변경 없음**: 응답 스키마 동일, dedup/페이징 기존 로직 그대로

## 후속 작업
- ✅ `SearchUiState.Phase.PostalCodeUnsupported` 제거
- ✅ `SearchViewModel.effectiveQuery` 5자리 우편번호 가드 추가
- ✅ `SearchScreen.EmptyResultPanel` 신설 — 우편번호 빈 결과 분기
- ✅ `SearchViewModelTest` 우편번호 정상 + sido 무시 + 4자리 일반흐름 케이스 추가
- ✅ SM-S938N installDebug 통과, 5개 시나리오(06236 정상/99999 빈결과/sido 무시/일반/페이징) 폰 검증

## 결정 근거 메모
- 형의 "이미 검증된 baseline 즉시 활용" 결단 + 헌법 §3.2(과한 추상화 금지) + `feedback_dead_code_removal`의 시너지. 새 Provider 추가는 외형적으로는 깔끔해 보여도 행안부가 native 지원하는 상황에선 동일 책임의 클래스를 두 번 만드는 셈.
- 우체국 OpenAPI 통합은 v2.0+ 마일에서 "행안부가 잡지 못하는 우편번호 케이스가 실측 1% 이상"일 때 재검토한다.
